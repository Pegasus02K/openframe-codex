# 설치 상세 절차

선택한 프로필의 버전·OS·DB와 현재 배포본·설치 스크립트에 맞춰 적용한다. 구체적인 경로·계정·포트·키·테스트 이름·정상 RC는 현재 세션에서 확인한다.

## 디렉터리·바이너리·환경

1. 환경 파일을 적용하고 `$SOURCE_BASE`, `$OPENFRAME_HOME`, `$TMAXDIR`, TCache 경로의 실제 대상이 의도한 신규 환경인지 확인한다.
2. 설치 샘플·스크립트와 설정이 요구하는 공통 및 제품별 디렉터리를 준비한다. 실행파일·라이브러리·copybook·임시·로그 경로는 실제 설정을 기준으로 확인한다.
3. 배포 아카이브의 내부 구조를 확인한 뒤 신규 설치 경로에 배치한다. `appbin`/`appbin64`, `lib`/`lib64` 같은 차이는 실제 경로와 APPDIR·라이브러리 설정을 맞춰 처리하고 기존 파일은 덮어쓰지 않는다.
4. Tmax·TCache·DB client·COBOL·Sort·OS별 전처리 도구의 환경과 라이선스를 확인한다. 다른 환경의 경로를 검증 없이 복제하지 않는다.
5. 포트·Tmax/TCache 공유 메모리 키와 `ds.DATASET_RESOURCE.DATASET_SHMKEY`를 기존 환경과 비교한다. 활성 자원과 중지 환경의 설정을 모두 포함하고 키는 정수로 정규화한다. 충돌하면 신규 환경의 값을 변경하며 기존 서비스나 IPC를 제거하지 않는다.
6. `openframe7-build`로 선택 제품의 빌드·설치·라이선스 생성을 완료하고 Tmax APPDIR에서 실제 서버와 TCache 바이너리를 찾는지 확인한다.

## DB 초기화와 설정

1. DB 접속 대상·계정·필요한 테이블스페이스와 신규 스키마 여부를 확인한다. 기존 객체가 있으면 초기화하지 말고 용도를 사용자와 확인한다.
2. 선택한 DB·OS의 활성 설정과 연결 정보를 준비한다. 암호화 값이 필요한 필드는 해당 도구와 제품 규약을 사용하고 평문·암호화 결과 모두 로그에 노출하지 않는다.
3. 현재 설치 스크립트·매뉴얼에서 DB 초기화, TCache 생성, 설정 import의 의존 순서를 확인한다. 필요한 캐시·설정·디렉터리를 준비한 뒤 OS에 해당하는 초기화 도구만 실행한다.
4. 확인 프롬프트가 있는 도구는 승인된 초기화 범위에서 입력을 별도로 전달해 셸의 후속 명령을 소비하지 않게 한다.
5. 초기화 명령의 종료 코드뿐 아니라 로그·생성 객체·유효 상태를 확인한다. 오류가 나면 이미 반영된 상태를 확인한 뒤 재시도하며 스키마 생성·캐시 초기화를 무조건 반복하지 않는다.
6. `ofconfig import` 후 실제 적용값을 조회한다. 파일의 기본값·현재값, DB와 설정 캐시를 구분한다. 기존 환경의 임시 변경·복원에는 `common-ofconfig-manage`를 사용한다.
7. 현재 설치된 제품의 오류코드 파일을 찾아 적재하고 결과를 확인한다.

## 기동·볼륨·시스템 라이브러리

- 대상 인스턴스·경로·포트를 확인하고 요청된 신규 환경만 기동한다. 필요한 서버와 TJES 상태를 확인하며 미기동 서버를 기능 성공으로 판단하지 않는다.
- 볼륨·장치·그룹·PDS는 실제 설치 설정과 도구 사용법을 확인해 준비한다. 기존 볼륨을 초기화하거나 기존 멤버를 덮어쓰지 않는다.
- TSO 등 관련 기능이 필요하면 PROC·맵·실행 디렉터리 등 선행 자원을 확인한다. 생성 도구의 RC와 실제 산출물·서버 상태를 함께 검사한다.
- 재기동이나 복구가 필요하면 현재 장애 증거와 영향 범위를 확인하고 세션의 사용자 요청 범위에서 결정한다. 특정 장애에서 사용한 강제 종료 절차를 공통 설치 단계로 적용하지 않는다.

## 데이터셋·JOB·제품 검증

1. 충돌 없는 테스트 데이터셋을 생성·조회하고 입력/출력 내용을 확인한다. 마이그레이션 도구의 신규 할당 여부와 이미 생성된 대상의 상태를 확인해 중복 할당을 피한다.
2. 삭제 검증은 종료 코드뿐 아니라 카탈로그 조회의 실제 항목 수로 확인한다. 보존할 산출물과 삭제 검증용 자원을 구분한다.
3. 현재 OS와 실제 설치 프로그램명을 확인해 최소 JOB을 작성한다. `batch-job-run`으로 실제 JOB ID·JOB 상태·STEP RC·동일 PTY SPOOL을 확인한다.
4. TSAM 테스트는 현재 스크립트의 생성·삭제 대상, copybook·키·레코드 정의와 Makefile target을 읽는다. 필요한 준비는 `base-tsam-create`로 수행한다. source와 설치본의 런타임 컴파일 cfg를 모두 확인한다.
5. 쓰기·읽기와 AIX/PATH 등 테스트의 입력 의존 순서를 확인해 실행한다. 기대값과 실제 측정값을 구분하고 JOB·STEP·애플리케이션 RC·SPOOL 및 최종 데이터/카탈로그를 함께 검증한다.
6. HiDB 등 DB 제품은 현재 테스트 소스와 구성에서 생성·초기화·적재·조회·갱신·삭제 순서를 확인한다. 선택 모드가 만드는 실제 테이블·인덱스에 맞춰 reset하며, RC 외에 기대 결과와 오류 처리도 검사한다.
7. 실패하면 의존 테스트의 연속 실행을 멈추고 원인·현재 데이터 상태를 확인한다. 준비나 reset이 필요하면 해당 테스트의 계약에 따라 수행한 뒤 필요한 범위만 재검증한다.

## 세션 결과

환경·브랜치/커밋·명령·실제 값·성공·실패·미실행 결과와 로그 위치를 해당 세션에서 사용자에게 보고한다. 장애 원인과 복구 범위는 현재 증거로 확인한다. 개별 실행 결과·환경값·우회 이력을 AGENTS.md나 스킬 참조에 추가하지 않는다. 사용자 요청에 따라 산출물을 보존하고 정리할 때는 해당 작업에서 만든 정확한 자원만 대상으로 한다.
