# OpenFrame 단위 테스트 작성

GoogleTest로 제품 코드의 동작을 검증하고 gcov로 새 제품 코드의 실행을 확인한다. 테스트 통과와 변경 코드 커버리지 충족을 각각 검증한다.

## Jira 이슈 작업에서 인계받기

- Jira 읽기·원인 조사 결과에서 이슈 ID, 재현 조건, 기대 동작, 대상 파일·함수, 프로필과 변경 내용을 이어받는다. 누락된 사실은 원문·소스에서 확인하고 추측하지 않는다.
- 코드 수정이 요청 범위에 포함되어 있으면 테스트 작성·등록·빌드·실행·gcov 검증·보고를 하나의 흐름으로 수행한다. 분석만 요청받은 작업은 테스트 계획까지만 작성한다.
- 테스트 파일만 추가하고 종료하지 않는다. 추가 지침 조건 또는 실행 환경 제한에 걸렸으면 사유와 남은 검증을 명시한다.

## 준비와 작성 위치

1. 루트 및 대상 제품의 `AGENTS.md`를 적용한다. 선택한 프로필의 환경을 적용하고 `$SOURCE_BASE`와 `$OPENFRAME_HOME`을 검증한다. 테스트 작성 권한을 제품 설치·DB 초기화·서비스 재시작 권한으로 확대하지 않는다.
2. 대상 함수·호출부·기존 테스트와 Makefile을 읽고 정상 동작, 경계값, 오류 처리 및 이슈 재현 조건을 정한다. 기대값은 제품 사양과 공통 구현에 근거한다.
3. 테스트 소스는 제품의 `test/unit/src/<대상 소스의 상대 경로>/`에 작성한다. 기존 파일이 있으면 확장하고 새 파일은 인접 아티팩트의 `gtest_<대상>.cpp` 또는 `test_<대상>.cpp` 명명 규칙을 따른다. 제품 소스 모듈 아래에 별도의 `test/` 트리를 만들지 않는다.
4. 지원 헤더·mock·stub과 바이너리·리포트 경로는 기존 구조와 Makefile 변수를 따른다. 기존 테스트를 이동하거나 중복 생성하지 않는다. 해당 제품에 `test/unit/src` 진입점이 없으면 기존 구조와 연결할 최소 Makefile 변경을 확인하고, 다른 제품의 경로·규칙을 그대로 복사하지 않는다.

## 테스트 작성 규칙

- `#include <gtest/gtest.h>`와 `TEST`, `TEST_F`를 사용한다. 공통 준비·해제는 `::testing::Test`의 `SetUp()`·`TearDown()`으로 묶고 각 케이스의 상태를 독립시킨다.
- 각 테스트 선언 바로 앞에 **3줄 이내의 주석**으로 입력·조건과 검증하려는 동작 또는 기대 결과를 명시한다. 파라미터 테스트도 각 입력이 나타내는 조건을 식별할 수 있게 한다.
- 이슈 해결 테스트라면 해당 이슈 테스트 묶음의 시작 부분에 **이슈 ID와 문제 내용·해결 후 기대 동작을 최초에 명시**한다. 첫 케이스의 3줄 이내 주석에 함께 적어도 된다. 개별 케이스의 목적 주석은 계속 유지하며 이슈 ID를 추측하지 않는다.
- 반환값뿐 아니라 필요한 출력 버퍼·구조체 필드·상태 변화·오류 코드·의존 함수 호출을 검증한다. 이후 실행의 전제조건은 `ASSERT_*`, 독립적으로 계속 검사할 값은 `EXPECT_*`를 사용한다.
- 정상·경계·실패 조건과 새 분기의 각 경로를 테스트한다. 이슈 회귀 케이스에는 문제를 유발했던 조건과 수정 후 기대값을 포함한다.
- 실제 대상 제품 함수를 호출한다. 대상 함수를 mock으로 대체하거나 구현을 테스트 코드에 복제하지 않는다. 외부 의존성만 기존 mock/stub 방식으로 격리하고 호출 인자와 결과를 검증한다. C 헤더는 선언 방식에 맞게 `extern "C"`를 적용한다.

다음 예시의 식별명·값·본문은 실제 대상으로 작성한다.

```cpp
// <ISSUE-ID>: 잘못된 길이 입력으로 버퍼 경계를 넘던 문제의 회귀 테스트.
// 용량보다 큰 입력은 오류를 반환하고 출력 버퍼를 보존해야 한다.
TEST(BufferTest, RejectsInputBeyondCapacity) {
    // 준비, 실제 제품 함수 호출, 오류와 출력 상태 검증
}

// 용량 경계와 같은 길이의 입력이 정상 처리되는지 검증한다.
TEST(BufferTest, AcceptsInputAtCapacity) {
    // 준비, 실제 제품 함수 호출, 반환값과 출력 검증
}
```

## 추가 지침이 필요한 경우

다음 중 하나에 해당하면 해당 테스트의 구현을 진행하기 전에 사용자에게 추가 지침을 묻는다.

- 아티팩트의 특성 때문에 단위 테스트 작성이 불가능한 경우.
- 테스트 코드가 지나치게 길어지는 경우(예: 200줄 이상).
- 기존 mock/stub으로 해결할 수 없어 새로운 모킹이 필요한 경우.

질문할 때 대상 파일·함수, 제약의 근거, 예상 코드 규모 또는 필요한 모킹의 범위와 가능한 대안을 설명한다. 사용자 답변 전에는 해당 구현을 진행하지 않고, 영향을 받지 않는 조사·검증은 계속할 수 있다.

## 빌드와 실행

1. 테스트 Makefile의 `SOURCES`, `TYPE`, `MODULE`, include·link·mock 설정, 제품의 `make/rules.gtest`, `rules.gtestpath` 및 상위 호출부를 확인한다. 기존 등록 방식에 맞춰 필요한 파일만 추가한다. gtest·pthread를 링크하고 자체 main이 없으면 gtest_main을 사용한다.
2. `.tbc`·`.pc`가 대상이면 해당 Makefile의 `make precomp`를 실행하고 생성 소스를 확인한다. 실패 원인을 해결한 뒤 반드시 재실행한다.
3. 현재 Makefile이 지원하는 타깃으로 빌드·실행한다. `test`, `gtest`, `gtest-build`, `gtest-run`, `cov`, `html`의 역할·의존성은 호출부에서 확인한다. 이름만으로 실행·수집 여부를 판단하거나 `make lcov`가 있다고 가정하지 않는다.
4. `--gtest_list_tests`로 신규 케이스 등록을 확인하고 필요하면 `--gtest_filter=SuiteName.TestName`으로 개별 실행한 뒤 관련 테스트 묶음을 실행한다. 실제 실행 건수·실패·skip과 종료 코드를 확인한다. 0건 실행이나 skip만으로 성공을 보고하지 않는다.

## gcov로 변경 코드 검증

1. 변경 diff에서 새 제품 코드의 파일·함수·실행 가능한 줄과 분기를 식별한다. 테스트 코드 자체의 커버리지로 제품 코드 검증을 대신하지 않는다.
2. 기존 coverage 빌드 경로를 사용하고 제품 코드 컴파일 및 최종 링크에 `--coverage` 또는 동등한 gcov 옵션이 적용됐는지 확인한다. 디버깅 가능한 최적화 수준을 사용하고 측정 산출물을 배포용 바이너리와 분리한다. 실제 로드한 라이브러리도 coverage 빌드 결과인지 확인한다.
3. 컴파일러와 호환되는 `gcov --version`을 확인한다. 이번 빌드의 `.gcno`와 이번 테스트 실행의 `.gcda`가 대응해야 한다. 누적 카운터를 방지하도록 확인된 대상 측정 데이터만 초기화하거나 격리하고 무관한 산출물은 삭제하지 않는다.
4. 테스트 실행 후 별도 출력 디렉터리에서 `gcov -b -c -o <오브젝트 또는 gcno 경로> <제품 소스 경로>`로 줄·분기 결과를 생성한다. 생성 C를 측정하면 원본 `.pc`·`.tbc` 변경과 생성 코드의 대응을 확인한다.
5. **새 실행 가능 줄마다 양의 실행 횟수**가 있는지 확인하고 새 조건 분기의 필요한 경로도 확인한다. `#####`·`=====` 등의 미실행 표시, 실행 횟수 0 또는 측정 누락이 있으면 케이스를 보강하고 재측정한다. 비실행 줄은 구분한다. 전체 모듈 비율만으로 새 코드 커버리지 충족을 판단하지 않는다.
6. 환경별 조건부 컴파일 등으로 측정할 수 없는 코드는 해당 줄·조건·필요 환경을 보고하고 미검증으로 남긴다. 새 코드 미커버 상태를 완료로 보고하지 않는다. 실행과 별개로 assertion이 요구 동작을 검사하는지도 확인한다.
7. lcov·genhtml은 필요할 때 보조 리포트로 사용한다. gcov의 변경 줄·분기 근거를 유지하고 생성 코드 제외 설정이 대상 변경을 숨기지 않는지 확인한다.

## 작성 후 보고

- 변경 파일과 `AS-IS → TO-BE`: 기존 검증 공백과 새 테스트가 검증하는 동작을 대응시킨다.
- **각 테스트 함수의 `SuiteName.TestName`**, 입력·전제조건, 테스트하려는 내용, 기대 결과, 실행 결과를 표 또는 항목별로 설명한다. 파라미터 테스트는 인스턴스·입력별 조건을 식별한다. 이슈 테스트는 ID와 회귀 조건을 포함한다.
- 빌드·실행·gcov 명령, 작업 디렉터리, 프로필의 버전·OS·DB 및 필요한 비민감 옵션을 기록한다.
- gcov 결과 파일을 제품 소스의 함수·줄과 연결하여 새 실행 가능 줄의 커버 수/전체 수, 관련 분기 결과 및 미커버·미측정 항목을 보고한다. 모듈 전체 비율과 변경 코드 결과를 구분한다.
- 성공·실패·생략과 실패 원인·필요 후속 검증을 명시한다. 코드 작성 완료와 실제 실행·커버리지 검증 완료를 구분한다.
